## The engine's limits, and a concurrent faucet · app

Asked for: find the engine's rate limiter, match our queue to it, and send as many payouts at once as it
allows.

**What the engine does** (`citizenwallet/engine` at `d5d7211`, the latest public commit):
- **No rate limiter.** Nothing in its code, and nothing in the nginx config it ships with.
- **One queue worker for every community on the chain.** Each pass waits a quarter of a second, takes up to
  ten operations, and carries each sponsor's share in one `handleOps` transaction. It answers a send once
  the transaction is broadcast, not when it lands.
- **A twelve-second limit on a send.** When it runs out, the engine answers "request timeout", but the
  operation stays in its queue and is sent anyway.
- **Random nonce keys, set by the engine.** `pm_ooSponsorUserOperation` gives each operation a nonce key at
  sponsorship: 24 random bytes cut to 100 bits, with the timestamp ORed in, leaving 76 random bits between
  two operations sponsored in the same second. Nothing changes it afterwards. We hash, sign and send it
  as-is, the engine's send path and bundler pass it through unchanged, and both the owner's and the
  paymaster's signatures cover it, so a changed nonce would fail on chain.
- **One failure fails the bundle.** The module reverts the whole `handleOps` when any call in it fails, so one
  failing operation fails every operation bundled with it.

**A double-pay hole, closed.** The backend took any error the engine sent back as a refusal and handed the
redemption code back. "request timeout" is not a refusal: the payout can still land, and the code could then
be redeemed a second time.
- `protocol.Client.Send` now treats only the thirteen errors the engine raises before queuing, and a failure
  to store the operation, as refusals.
- Anything else, including messages it has never seen, means "may have been accepted", and the code stays
  spent.

**The dispatcher sends in waves.**
- **The old rule was wrong.** Since Oct 22 (`5aa4df7`) it sent one operation at a time, on the belief that
  two sponsored together could share a nonce. They cannot.
- **Waves of ten.** Up to ten payouts, each its own operation, are submitted together, so the engine can carry
  them in one transaction. The next wave goes when the engine has answered, not when the transfers land.
- **At most one engine pass of ours waits in the queue,** well inside the twelve seconds.
- **Settling in the background.** Up to 60 payouts can settle at once, which bounds the polling load on the
  read RPC.
- **One payout per person at a time.** Payouts are matched to transfers by recipient and amount, so two to the
  same person in flight together could claim each other's.
- **The lock is a read/write lock.** Payouts submit together under the read lock. Key rotations, the legacy
  sweep, the recovery owner and the batcher approval take the write lock, and still exclude payouts.
- **The transfer search pins each operation's transaction separately.** A wave can land in one transaction or
  several.

# Round 2 — Mon Nov 16, from 11:33: the nonces checked, and round 1 committed

**0.1h** (0.111h) measured, 11:33:00–11:39:38, the same sitting.

- **The exposed key's repository**, linked for PJ, and left unnamed in this file while the key may be live.
- **Who sets the nonces.** Asked: check that our dispatcher sets the nonces and that the engine does not
  overwrite them.
  - Our dispatcher does not set them. Every operation goes to `pm_ooSponsorUserOperation` with nonce 0, and
    the engine sets the key there.
  - Nothing changes it afterwards. We hash it with the entry point's `getUserOpHash`, sign it, journal it
    and send it unchanged. The engine's send path and bundler pass it through untouched. Both the owner's
    signature and the paymaster's (`pack(sender, nonce, selector)`) cover it.

  timestamp, which leaves 76 random bits between two operations sponsored in the same second. The
  dispatcher's comment and round 1 above were corrected before either was committed.
- **Bundling still works on the engine's nonces.** Each operation is checked against its own key, so a wave
  only fails if two keys collide: about 2⁻⁷⁰ across ten.
  - The real exposure is depending on the engine's generator.
  - Setting our own key through `pm_sponsorUserOperation`, which keeps the nonce it is given, was offered
    and not yet taken up.
