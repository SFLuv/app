# Round 1 — Mon Nov 16, from 10:33: questions, the contracts repo's stray submodules, and last week's missing time

## Questions answered

- **Does Ponder's key have to be rotated for anything to work?** No: it is for security only. The key may
  already be out: the hook route pinged a caller's URL with the key attached before storing anything, so an
  attacker could take the key and leave no hook behind. A holder could post forged transfers to
  `/ponder/callback` and send real users fake "payment received" notices. Ponder's `ADMIN_KEY` and the backend's
  `PONDER_KEY` must change together, after the first deploy has dropped foreign hooks. Also worth checking: the
  backend's own `ADMIN_KEY` is a separate variable with the same name as Ponder's.
- **Does the batcher need an approval from every user?** No. Only the faucet Safe calls it, and the backend
  approves it once at boot. Neither client calls it, and receiving a batched transfer needs nothing. An approval
  at login would only be worth adding if users ever batch their own payments.

## The contracts repo · contracts, app

- **The embedded submodules.** Five folders under `lib/` were staged as gitlinks with no `.gitmodules` entry:
  `bera-contracts`, `contracts`, `core`, `layerzero`, `lz-address-book`. They are the zapper and migrator
  branches' submodules, left behind when `main` was checked out, then caught by a `git add`, and nothing on
  `main` or this branch imports them.
  - **The fix:** unstaged from the index only, so the folders and a local edit inside `lib/bera-contracts`
    stay on disk for those branches, and listed in this clone's `.git/info/exclude` so a `git add -A` cannot
    take them again.
  - **Nothing needed committing for them.** They had never been committed, so the batcher commit `8fabb61`
    was already on the remote.
- **A fresh clone exposed a wrong hash.** Built from a fresh clone of the remote branch, the batcher came out
  as `0x6bb04297…fd51`, not the `0x744ebebb…b855e0` the backend pinned on Friday. Diffing the two builds'
  compiler metadata found one difference, `settings.remappings`: Foundry auto-detects a remapping for every
  folder under `lib/`, so the stray folders added 21. A deployer working from the repo would have been
  refused by the backend.
  - **contracts `140ac56`:** the `batcher` profile sets `auto_detect_remappings = false`, so only
    `remappings.txt` counts, and the deploy instructions start with `forge clean`, because a cached artifact
    kept the old metadata through the first attempt.
  - **Checked:** after a clean build, the local build, with the stray folders still present, and a fresh clone
    produce identical metadata and the same hash, `0x6bb04297721b59d7a65386999718f39edb4df5408d7b11a6bb0067d21c28fd51`.
    12 of 12 tests pass under both profiles.
  - **app:** `protocol.BatcherCodeHash` now pins that hash.
