## Asked for

QR perk codes lock as redeemed when the redemption did not complete: a queued transaction that does not
clear, or an error after the window the backend watches a send for, and the code is never handed back. There
should be a natural settlement path that unlocks unused codes. The code's transaction should be recorded, so
that a scan which finds a code redeemed can check that transaction and confirm it really was. Security comes
first: nothing here may let one code be paid twice. Before starting, check that Sanchez has not already
pushed fixes for any of the six.

## What Sanchez already had

None of the six items is done on any branch, open PR or `main` in app, mobile-app or webpage. Two pieces of
his bear on this one and are already in `main`: the payout confirmation sweep (#202) and the unconfirmed
send handling (`faucet-confirmation-fix`, by patch). His Nov 8 note ends with "Not done here: releasing a code
automatically when the sweep confirms its payout was never sent", which is this item. Batching is off since
#229 (item 5). His website CMS (`website-cms.md`) is where item 6's editor belongs.

## What was wrong

- **A send abandoned mid-flight was never looked at again.** A deploy or crash between spending a code and
  recording an outcome leaves the payout `pending` with no marker. Neither the sweep nor a retry touches
  such a row, so its code stayed spent for good. The same happened when the token's decimals could not be
  read: that path answered 500 without handing the code back.
- **Nothing was recorded that could be checked.** A payout whose confirmation was lost kept only a
  recipient and an amount. The operation it went out as was in a log line and nowhere else.
- **The sweep could pay twice.** It concluded a payout "never sent" an hour after a later faucet operation
  landed, on the grounds that operations take their nonces in order. They do not here. Read from chain, the
  engine gives every operation its own random nonce key at sequence zero, and this EntryPoint emits no
  `UserOperationEvent`. An operation still queued in the engine could land after its payout had been
  concluded lost and paid again, which is exactly the queue-not-clearing case. This logic has been live
  since Oct 25.

## Features

### Payouts written down before they are sent — 0.101h build, 0.086h rebuild · app

- **The journal.** Migration 1.83. Each operation's hash, sender, nonce and paymaster `validUntil` go onto
  its ledger row after signing and before `eth_sendUserOperation`. If that write fails, nothing is sent.
  The old key's path records its sender, so a row with nothing written down provably never reached a send.
- **Settled from the chain, without timing.** `getNonce(safe, key)`, read 30 blocks deep, moves past the
  operation's sequence in the block that included it. Then the code:
  - binary-searches for that block;
  - decodes the `handleOps` call listing the operation;
  - reads that transaction's receipt.

  That gives one of three answers:
  - **Paid**, with the transfer claimed from the receipt.
  - **Sent nothing:** the operation ran without the transfer.
  - **Can never land:** it was never included and its `validUntil` (seven days) has passed.

  Anything else waits.
- **The dispatcher asks once** when its 90-second watch runs out. An operation that ran without the
  transfer now hands the code back at once, instead of leaving it spent until the sweep.
- **The sweep's double-pay fixed.** Rows with nothing written down, from before this, are concluded lost
  only once seven days and a day's margin have passed since their last attempt. That is the paymaster's
  window on every payout checked. A row abandoned before anything was written down is concluded at once.
  Its queue died with its process.

### "Already redeemed" is checked, not taken at its word — inside the build above · app

- A rescan of a spent code reads its payouts.
  - **Paid or held:** the code stays spent.
  - **Unresolved:** it is put to the chain there and then, at most once a minute per payout, and only
    once the sweep would take it, so a send still running is never disturbed.
  - **Every attempt provably sent nothing**, or none reached the ledger: the code is handed back and
    redeemed for the person scanning.
- **Never too early.** It does not do this for a redemption younger than 15 minutes, or for an undated
  redemption from before this change.
- **What the scanner hears.** The person whose payout is still settling hears "payout pending", as
  before. Anyone else hears "code pending". Older apps show their generic error for that.
- **One guarded release.** Every path that hands a code back goes through `releaseRedemption`. It locks the
  code's row and refuses while any payout for the code is paid, held, in flight, or of unknown outcome.
  The `source_ref` unique index on standing payouts stays as the second line.

**0.1h** (0.115h), measured: 10:28:37–10:35:32, the same sitting as round 6. The gap between them,

## What the audit found

Every path that concludes a payout "not sent" or hands a code back, rechecked against the contract source
and the callers of `Pay`.

- **Expiry is enforced on chain.** This is Citizen Wallet's `CommunityModule` in `citizenwallet/contractforge`,
  as published. The deployed module is upgradeable, so that holds while Citizen Wallet keeps it so. The
  paymaster requires `currentTime < validUntil`, and the module rejects `block.timestamp > validUntil`. The
  Safe owner's signature covers `paymasterAndData`, so the window cannot be swapped. A failing call reverts
  the whole `handleOps`, nonce bump included, so a consumed nonce means the operation ran.
- **The window was the same in October.** Payouts from Oct 28–29 carry random nonce keys and the same 7-day
  window. The 8-day rule for older rows holds for every row unresolved today.
- **`Pay` sent a payout again whenever its row was already pending.** That covers an attempt still in flight
  and one abandoned mid-send. Two overlapping calls for a workflow step, or the loop retrying a step whose
  process died, sent a second operation while the first could still land. This hole was older than round 6.

## The fixes · app

- **`Pay` sends an existing row only if this call re-armed it.** Re-arming is the conditional update from
  failed-not-sent, so exactly one caller wins. Any other existing pending row is refused with
  `ErrPayoutInFlight`. The refusal never releases a code. Both workflow payout loops leave such a step
  alone, rather than marking it awaiting confirmation over the attempt that is sending it.
- **Every "not sent" conclusion is pinned** to the operation hash and sender the row carried when the chain
  was asked. A send writes its operation onto the row before it goes, and only while the row is pending.
  The two updates cannot both succeed: a conclusion loses to a send recorded since, and a send cannot
  record itself onto a concluded row, so it never goes out.
- **A row with no operation recorded is concluded lost only if all of these hold:**
  - the 7-day window plus a day has passed;
  - no transfer of that amount to that recipient exists anywhere in its range, held by anyone (one held
    by another payout might be this one's, so that case is logged for an admin);
  - it was not the old key's send, which has no expiry.
- **`validUntil` is trusted only as a window**: before it comes a `validAfter`, within 30 days. Swapped
  words, zero or an outsized span are not believed, and the operation is then never concluded expired.

  and is all or nothing.
- **Why whitelisting it is safe.** An allowance granted to it can be spent only by the account that granted
  it, calling it itself. So a sponsored account can do nothing it could not already do with a plain

  page is one versioned document, `site_content` key `resources`, holding How to videos, books, podcasts and
  technical links. Every item can be reordered and switched off without being deleted. Saves are refused
  if someone else saved since, and history and restore work as the banner's do.
- **Who can edit it.** A new private credential, `website_resources` ("Website editor: resources page"),
  listed under Website editor. An admin or a Website editor holds it implicitly.
- **YouTube links.** Accepted in the forms people paste (`watch?v=`, `youtu.be/`, `/embed/`, `/shorts/`,
  `/live/`, a bare id), from YouTube's own hosts only. The server keeps the id it reads and builds the
  embed address itself, so nothing typed becomes a frame's source. Book links and technical links go
  through the CMS's link check: `https://` or a path on the site, never `javascript:`.
- **Migration 1.84** adds the credential and seeds the page as it was, with
  `docs.celo.org — Discover Celo` in place of `polygon.technology`. Nothing else changes for a visitor on
  deploy. The How to section starts empty, and is hidden until it has a video.

### Backend · app

- `GET /site/resources`, public, returns only switched-on, complete items, with embeds and cover URLs
  resolved. `GET`, `PUT` and `POST …/restore` under `/admin/site/resources`, behind the new credential.
  Edits go into the Website tools' activity log.

### Admin panel · app

- **A "Resources & how-to" tab** in Website. It has four sections (How to videos, What we're reading,
  Podcasts, Get technical), with add, reorder, switch off and delete, and save and publish.
- **Previews:** a thumbnail as soon as a YouTube link is pasted, and cover uploads through the CMS's
  uploader. Uploaded covers are kept by its cleanup for as long as a version refers to them.

### Website · webpage

- **The page reads `/site/resources`,** cached 30 seconds like the CMS's other parts, so an edit shows within
  about half a minute.
- **How to comes first:** each video's title, description, embed and a "Watch on YouTube" link. A section
  with nothing in it is not shown.
- **The built-in fallback copy** has Celo in place of Polygon too.

## Checked

Against a scratch Postgres from `cmd/init`, through migration 1.84:

- **The seed:** the credential sits under Website editor, and the seeded version carries its import note.
  The public route serves 3 books, 2 podcasts and the Celo link, with Polygon nowhere.
- **Permissions:** an admin and the credential's holder may edit; someone without it may not; and the holder
  may not edit the banner.
- **Saving:**
  - a Vimeo link, a shown video with no link, and a `javascript:` link are each refused with a message;
  - a draft that is switched off saves;
  - a `youtu.be` link is stored as its id and published as an embed;
  - a save from a stale version gets a 409;
  - restoring version 1 brings back the import, and the history reads v1 to v4.
- **YouTube parsing,** 12 cases. Lookalike hosts (`youtube.com.evil.example`), other hosts and malformed ids
  are refused. One case found the parser returning a malformed id alongside `ok=false`; no caller used it,
  and it now returns nothing.
- **The real site:** its dev server rendering `/resources` from the backend's own JSON shows How to first,
  then the embed, 3 books, 2 podcasts and the Celo link, in order. With no API it falls back to the built-in
  copy: Celo, no How to.
- Backend build, vet and `gofmt` are clean. Frontend `tsc` reports nothing in the changed files, and the
  website's `tsc` passes.
- **Not checked:** the editor in a browser.
